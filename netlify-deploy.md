# Як захостити сайт «АКТИВ» на Netlify

Покроково, від порожнього репозиторію до працюючого домену з живим Sanity.
Усе, що потрібно з коду, у проєкті вже є: `netlify.toml`, адаптер, вебхук.

---

## Перед початком: одне попередження

**На проді зараз стоять чужі фотографії.** У `lib/photos.ts` чотирнадцять
знімків із Unsplash, вони підключені прямими посиланнями на чужий CDN.
Для показу замовнику це нормально, для живого сайту юридичної компанії —
ні: посилання може відвалитися будь-коли, а ліцензія Unsplash не покриває
все, що завгодно.

Це не блокує запуск, але поставте собі це як обов'язковий пункт перед
тим, як давати домен клієнтам. Замінюються вони в одному файлі.

## Крок 1. Репозиторій

Netlify збирає з git. Локальної папки недостатньо.

```bash
cd "C:\Users\Vlada Hnatok\Desktop\Шайко - сайт"

git init
git add .
git commit -m "Сайт ЮК «АКТИВ»: перша версія"
```

`.gitignore` у проєкті вже правильний: `node_modules`, `.next`, `.env.local`
та `.env*.local` до репозиторію не потраплять. **Перевірте це до пушу**, бо
токен Sanity у публічному репозиторії — це доступ на запис до всього
контенту:

```bash
git ls-files | Select-String "\.env|node_modules"
```

Порожній результат — усе гаразд. Якщо щось знайшлося, не пушіть: спершу
приберіть файл з індексу (`git rm --cached <файл>`).

Далі створіть порожній репозиторій на GitHub (**без** README і .gitignore,
інакше буде конфлікт) і відправте код:

```bash
git remote add origin https://github.com/ВАШ-АКАУНТ/aktiv-site.git
git branch -M main
git push -u origin main
```

**Публічний чи приватний.** Робіть приватним. Публічність нічого не дає,
а в коді є структура контенту клієнта й коментарі про його внутрішні
процеси. Netlify однаково бачить приватні репозиторії.

## Крок 2. Створити сайт на Netlify

1. `app.netlify.com` → **Add new site** → **Import an existing project**
2. **Deploy with GitHub** → дозволити доступ → вибрати репозиторій

Налаштування збірки Netlify підхопить з `netlify.toml` і **пропонувати
нічого не буде** — так і має бути. Що там написано:

| Параметр | Значення | Чому саме так |
|---|---|---|
| Build command | `npm ci && npm run build` | `ci` ставить рівно те, що в `package-lock.json`. `install` підняв би мінорні версії й міг зібрати не той код, що перевірено локально |
| Publish directory | `.next` | цього чекає адаптер |
| Node version | 22 | `package.json` вимагає `>=22`; на Netlify типово нижча, і збірка впала б |
| Plugin | `@netlify/plugin-nextjs` | Netlify ставить сам за записом у `netlify.toml` |

**Поки не натискайте Deploy.** Спершу змінні — інакше перша збірка
пройде, але сайт покаже статичні тексти з коду замість Sanity, і ви
витратите час на пошук неіснуючої проблеми.

## Крок 3. Змінні середовища

**Site configuration → Environment variables → Add a variable.**
Для кожної вибирайте scope **All scopes** (і збірка, і рантайм).

### Обов'язкові

```
NEXT_PUBLIC_SANITY_PROJECT_ID    q2tr45a7
NEXT_PUBLIC_SANITY_DATASET       production
NEXT_PUBLIC_SANITY_API_VERSION   2026-01-01
SANITY_REVALIDATE_SECRET         <довгий випадковий рядок>
```

Секрет для вебхука згенеруйте так (і збережіть — він знадобиться на
кроці 6):

```powershell
-join ((48..57) + (97..122) | Get-Random -Count 40 | % {[char]$_})
```

### Не додавайте зараз

- `SANITY_API_READ_TOKEN` — потрібен **лише для приватного датасету**.
  Ваш публічний: сайт читає його без токена. Додасте, якщо колись
  закриєте датасет.
- `SANITY_API_WRITE_TOKEN` — це токен **на запис**, потрібен тільки
  локально для `npm run seed`. На хостингу йому робити нічого, а лежати
  там він буде як зайвий ризик.
- `SANITY_STUDIO_*` — читає CLI студії, яка запускається у вас на
  комп'ютері, а не на Netlify.
- Блоки Firebase, аналітики й Telegram з `.env.example` — це етапи 4 і 5,
  їх ще немає в коді.

### Чому префікси не взаємозамінні

`NEXT_PUBLIC_*` Next вбудовує в браузерний бандл під час збірки. Усе
інше залишається тільки на сервері. Тому `SANITY_REVALIDATE_SECRET` **без**
префікса — інакше секрет поїхав би у вихідний код сторінки й перестав
бути секретом.

## Крок 4. Перша збірка

**Deploy site.** Перша збірка — близько 2–4 хвилин: 135 сторінок
генеруються заздалегідь.

Ви отримаєте адресу вигляду `random-name-123456.netlify.app`. Відкрийте й
перевірте по порядку:

1. **Головна** — заголовок «Рішення без виконання — не результат»
2. **`/practices/likvidatsiya-bankrutstvo/alternative-liquidation`** — сторінка
   практики відкривається, не 404
3. **`/sanity-check`** — сторінка діагностики; має бути зелено по
   `NEXT_PUBLIC_SANITY_PROJECT_ID` і «доступ: public»
4. **«Нам довіряють»** — якщо в ленті їде «Моторола», Sanity живий
5. **Мова** — `/` віддає українську без префікса, `/en` і `/ru` працюють

### Якщо сторінки практик дають 404

Найімовірніше `npm ci` не встиг, і збірка впала частково — дивіться
**Deploys → лог**. Другий варіант: у git не доїхали файли. Перевірте:

```bash
git ls-files app | Select-String "practices"
```

Має бути два файли: `[category]/page.tsx` і `[category]/[slug]/page.tsx`.

### Якщо сайт показує тексти, але не ті, що в студії

Це не помилка збірки. Відкрийте `/sanity-check` — вона розрізняє шість
різних причин «контент не підтягується» й пише, яка саме ваша. Найчастіші
дві: не задано `NEXT_PUBLIC_SANITY_PROJECT_ID` у scope збірки, або
документ у студії не опублікований (лишився чернеткою).

## Крок 5. Домен

**Domain management → Add a domain** → `aktiv-alb.com`.

Netlify покаже, які записи поставити в реєстратора. Два шляхи:

**Простіший — Netlify DNS.** Ви змінюєте NS-записи домену на
netlify-серверні, і далі все керується з Netlify, включно з
сертифікатом. Мінус: якщо в домену є пошта чи інші сервіси, їхні
записи треба перенести теж, інакше пошта відвалиться.

**Безпечніший — лише A/CNAME.** Домен залишається в реєстратора, ви
додаєте два записи:

```
A      @      75.2.60.5
CNAME  www    ВАШ-САЙТ.netlify.app
```

Пошта й інші записи не торкаються. Саме це і виберіть, якщо на домені
вже є робоча пошта.

**Сертифікат** Netlify видасть сам (Let's Encrypt) за 5–20 хвилин після
того, як DNS розійдеться. Увімкніть **Force HTTPS** — інакше сайт
залишиться доступним і по http.

### Старий сайт на WordPress

Не вимикайте його, поки новий не працює на домені. І окремо вирішіть
питання **301-редиректів**: на старому сайті були адреси вигляду
`/practice/alternative-liquidation/`, їхня пошукова вага накопичена за
18 років. Ці шляхи вже збережені в Sanity у полі `legacyPaths` у
кожної практики — редиректи можна зібрати з них, але зроблено це ще не
було. Без редиректів частина позицій у Google просто зникне.

## Крок 6. Вебхук Sanity

Без цього кроку правки в студії доїжджають до сайту **до п'яти хвилин**
або не доїжджають зовсім до наступної збірки. Сторінки генеруються
заздалегідь, і хтось має сказати кешу, що документ змінився.

`sanity.io/manage` → ваш проєкт → **API** → **Webhooks** → **Create webhook**:

| Поле | Значення |
|---|---|
| Name | `Netlify revalidate` |
| URL | `https://aktiv-alb.com/api/revalidate` |
| Dataset | `production` |
| Trigger on | Create, Update, Delete |
| Filter | `_type in ["practice","practiceCategory","post","teamMember","siteSettings","quiz","homePage","aboutPage","teamPage"]` |
| HTTP method | `POST` |
| API version | `v2021-03-25` |
| HTTP Headers | `x-revalidate-secret` = ваш `SANITY_REVALIDATE_SECRET` |

**Перевірка.** Відкрийте `https://aktiv-alb.com/api/revalidate` у
браузері — маршрут відповідає на GET короткою довідкою про свій стан, без
секрету й без даних. Далі змініть у студії будь-який заголовок,
опублікуйте — і оновіть сторінку сайту. Зміна має бути видна одразу, а не
через п'ять хвилин.

Якщо не працює: у Sanity в списку вебхуків є журнал спроб з кодом
відповіді. `401` — не зійшовся секрет (перевірте, що в Netlify і в
заголовку вебхука рядок **однаковий**, без пробілів на кінцях). `404` —
не той URL.

## Крок 7. CORS для студії

Студія запускається у вас локально (`npm run studio`, порт 3333) і
звертається до API Sanity з браузера. Якщо колись будете відкривати її з
іншої адреси — `sanity.io/manage` → **API** → **CORS origins** → додати
походження. Для локальної роботи `http://localhost:3333` там уже має
бути; якщо студія раптом перестала бачити дані, дивіть сюди першим.

## Крок 8. Після запуску

### Що відбувається при кожному пуші

`git push` у `main` → Netlify збирає й публікує сам. Гілки та pull
request'и отримують окремі **deploy preview** адреси — зручно
показувати правки замовнику, не торкаючись живого сайту.

### Відкат

**Deploys** → вибрати попередню успішну збірку → **Publish deploy**.
Повертає миттєво, без перезбірки. Це головна причина не бути
надто обережним з деплоями.

### Перед кожним пушем

```bash
npm run check
```

Одна команда: типи, схеми Sanity, GROQ-запити й прогін калькулятора
на всіх 432 комбінаціях відповідей. Зелений результат тут означає, що
збірка на Netlify не впаде з тих причин, які можна було побачити
заздалегідь.

Окремо варто знати про `npm run check:groq`: він розбирає всі 18
запитів справжнім парсером. Помилка в GROQ не роняє збірку й не
фарбує сторінку — запит просто повертає порожнечу, і блок тихо
показує статичний текст із коду. Виглядає це як «Sanity не
підключений» при повністю робочому підключенні, і шукати таке
доводиться довго.

### Чого на Netlify ще немає

- **Форма заявки нікуди не пише.** Зараз лід іде в консоль сервера.
  Приймання заявок — етап 4 (Firestore + `/admin`).
- **Аналітики немає.** Події в `dataLayer` формуються, але контейнер
  GTM не підключений — етап 5.
- **Фотографії чужі.** Див. попередження на початку.

## Коротка шпаргалка

```
1. git init → commit → push на GitHub (приватний)
2. Netlify → Import from GitHub → вибрати репозиторій
3. Environment variables: PROJECT_ID, DATASET, API_VERSION, REVALIDATE_SECRET
4. Deploy → перевірити /sanity-check і сторінку практики
5. Domain → A + CNAME → Force HTTPS
6. Sanity → Webhooks → /api/revalidate з тим самим секретом
7. npm run check перед кожним пушем
```
